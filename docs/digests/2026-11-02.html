DBMS Weekly — 2026-11-02 (week of Nov 2–8)

Days before 19 RC2, Andrew Dunstan reverted the "complete" immutability check for to_json/to_jsonb after it let JSON_ARRAY()/JSON_OBJECT() expression indexes go stale and return wrong rows; anything built on 19rc1 that depends on it must be redefined before dump/restore or pg_upgrade. Two of last issue's checkpoint races (ROLLBACK PREPARED, multixact creation) were fixed back to 14, and the 18.7/17.12/16.16/15.20/14.25 notes — "a good bit longer than average" — collect Memoize and Sort-node wrong results, a pg_trgm GiST corruption fix that needs a REINDEX, incremental backups restoring stale visibility-map bits, and a walsender lost wakeup that stalled synchronous commits for up to 10 s. The list's meta-story was AI-found bugs: one tester asked how to submit more than 1,000, Peter Geoghegan said he holds about 25 unreported ones and posted his own LLM-written rival to the nbtree prefix-compression patch. On the blogs, failover was the theme: Dimitri Fontaine killed primaries in a five-region pg_auto_failover + logical-replication system and counted every hole and duplicate, and Ubicloud and PlanetScale gave opposite answers to "how do you know the old primary is dead". Nikolay Samokhvalov put UUIDv4 keys at 0.62–0.69× an ordered key's insert rate once the index outgrows memory, Franck Pachot showed TOAST stops compressing mid-sized documents on 16/32 KB pages, AWS proposed upstream a constant-time binlog commit for huge MySQL transactions, Thomas Neumann took apart GenDB-V's 22–61× TPC-H claim, and PostHog explained why it is leaving DuckDB after five months.

PostgreSQL

  • UUIDv4 vs UUIDv7: what a random primary key costs in Postgres — 18.6, 16 clients, one single-row INSERT per transaction, synchronous_commit = on, three tables differing only in the primary key (v4, v7, int8), hypotheses written down with falsifiers before the runs. Results: (Nikolay Samokhvalov · postgres.ai)
    • While the index fits in memory the key barely matters: UUIDv4 ran at 0.95–1.10 of v7, because the shared WAL flush sets the rate.
    • With a 1 GiB shared_buffers under a 3 GiB cgroup cap, v4 starts to fall at ~26 M rows, when its primary key outgrows shared_buffers. At 100 M rows it ran at 0.62–0.69 of an ordered key on the same server, roughly one buffer read and one dirty-page eviction per insert, done by the backend itself.
    • v4 wrote 1.5–1.9× the WAL per row at 90–100 M rows, because every checkpoint re-images each leaf it touched; its primary key was 33% larger than v7's.
    • v7 generated in the application with client clocks spread over ±60 s produced an index 69% full with 45% of leaves out of order, so generate it in the server.
    • ORDER BY id DESC LIMIT 100 on a v4 table returns the largest random values, not the newest rows.
    • The predicted 0.5× was never reached. The post compares its results with Vondra's 2018 numbers (15–20% once past RAM, on SATA disks).
  • Postgres logical replication beyond one writer — rebuilds what BDR did in 2014 from stock features: four regions plus a warehouse, each a pg_auto_failover group (monitor + three nodes), linked only by core logical replication. Row filters (15) and origin = none (16) prevent loops, failover slots with synchronized_standby_slots (17) keep slots across failover, and 18/19 count conflicts and sync sequences. A Docker lab is included and every number comes from three runs. (Dimitri Fontaine · tapoueh.org) [by pg_auto_failover / pgcopydb author]
    • A failover-slot consumer at ~25 rows/s: a planned failover lost and duplicated nothing (1.4–2.2 s); kill -9 on the primary gave 2–4 duplicates and no holes (51–52 s); with synchronized_standby_slots emptied, 3–13 rows were missing and 69–92 rows had reached the consumer but not the new primary.
    • With 2,000 concurrent writes in each of four regions and two cascades, every node ended with exactly 8,000 rows.
    • DDL is the remaining gap. Pausing writers costs 0.9–1.5 s; pgcopydb captures DDL with an event trigger and pg_logical_emit_message. A fifth region joined a 600,000-row system with five statements.
    • Two writers updating the same 1,000 keys at 2,000 tps each are only counted as conflicts (18), not resolved.
  • Fencing a Postgres primary that might still be alive — promotion alone does not stop the old primary. A session can SET synchronous_commit = local, the other standby in an ANY 1 quorum still acknowledges, and a COMMIT whose sync wait is cancelled is already in the local WAL. pg_ctlcluster stop is undone by auto-start on reboot, and a pg_hba.conf reload only affects new connections, so long-lived PgBouncer server connections survive it. The fences that work: (Furkan Sahin · clickhouse.com / Ubicloud) [vendor blog — substantive]
    • bare metal: ip link set vetho<vm> down on the host, which cuts clients, replication and WAL upload in one step
    • AWS: security groups are stateful and stop-instances is slow, so every server gets a second "user" NIC that is force-detached
    • GCP: a Dynamic NIC is deleted
    • All mechanisms run in parallel and the first success proceeds. If every one fails, the standby promotes anyway; this fail-open behaviour is deliberate and pinned by a test. Based on the author's PGConf.EU talk.
  • Designing a reliable unplanned failover — the sequel to last issue's planned switchover, and the opposite answer to the same question. Neki uses no lease; it asks the replicas. It fails over only when at least one reachable replica reports broken replication (pg_stat_wal_receiver) and none contradicts it, and it waits if it can reach neither the primary nor any replica. Short TCP keepalives, tcp_user_timeout and wal_receiver_timeout are tuned so that a crash, rejected connections, dropped packets and a frozen process all end the same way, as "replication broken". Under ANY 1 (R1, R2, R3) a primary nobody can ack cannot commit. Postgres has no STOP REPLICA IO_THREAD, so the replicas are kept from reconnecting to a returning primary by prefixing its host in primary_conninfo with //. (Shlomi Noach · planetscale.com) [vendor blog — substantive]
  • PostgreSQL document compression: TOAST thresholds, storage policies, and page size — TOAST tries to compress a value only once the whole tuple passes a hardcoded quarter-page gate (~2 KB at 8 KB pages). toast_tuple_target changes only the reduction target: lowering it cannot trigger compression, and raising it suppresses more. On source builds of 19rc1, a 3,868-byte JSONB document no longer compresses with 16 KB pages and a 7,708-byte one stops at 32 KB, because the gate scales with the block size. WiredTiger, by contrast, compresses whole leaf pages across documents. He links the 2019 compress_tuple_target thread (Deolasee, Dunstan, Paquier) and proposes an activation threshold separate from the inline target, or per-column eligibility. This matters to DocumentDB, which stores BSON through TOAST. All SQL and Dockerfiles are included. (Franck Pachot · dev.to)
  • Patroni, Ubuntu 24.04, and two unplanned PostgreSQL failovers — an 8-hour load died with "SSL connection has been closed unexpectedly". The cause: unattended-upgrades upgraded zlib1g at 06:19:03, and needrestart ran systemctl restart on a list that included the custom Patroni unit. With the default KillMode=control-group, the stop signal reached Postgres too: smart shutdown, then fast, then failover.   • [hackers] The checkpoint-race family: two fixed, two pending. All four have the same shape: a WAL record is written before a file or SLRU change, and a checkpoint can start in between. (Shihao Zhong; Michael Paquier, Heikki Linnakangas, vignesh C · pgsql-hackers/-committers) [committed] + [patch posted]
    • Racing in ROLLBACK PREPARED and checkpoint: DELAY_CHKPT_START is now set around the abort record and the pg_xact update, so a rolled-back prepared transaction can no longer come back after a crash and then be committed. Committed to 14+ on Nov 2. Paquier: the bug is "as old as the introduction of 2PC back in 2005".
    • checkpoint can lose a multixact created during its start: the race that could make an old row version visible again next to the new one. Committed to 14+ on Nov 3. Heikki: "Interesting that we recognized that problem in TruncateMultiXact(), but missed it in the much more frequently used MultiXactIdCreateFromMembers()". He left out the test.
    • hash bucket allocation and CLOG truncation: vignesh C found that v1's DELAY_CHKPT_START in _hash_alloc_buckets() stays set if an ordinary ERROR (e.g. out of disk space) is raised in between. v2 instead extends the file before writing the WAL record, as heap extension does. There are back-branch variants, and a 0005 for a further multixact case vignesh found [patch posted]

If a savepoint catches the error, AbortSubTransaction() doesn't clear the flag, so every checkpoint waits until the transaction ends [open]

Research & cutting edge

  • Correctness firewalls for synthesized database components — a design-pattern answer to "coding agents can now write instance-optimized engine parts": put the synthesized component behind a boundary where it can change performance but never results. Three case studies: an advisory firewall for cardinality estimation (a wrong estimate costs only time), a guarded one for sorted-data search (results are checked), and a certified one for compression (the round trip is verified). In early runs, synthesized search is up to 3× faster than human-designed learned indexes and synthesized text compression is 1.5× smaller than Zstd. Ends with a research agenda on what correctness costs. (Amiri, Binnig, Kipf, Kraska, Marcus, Wehrstein, Wu, Yu, Zhao) [paper]
  • GenDB-V: AI-generated and formally verified database engines — agents generate specialised query implementations together with proofs against SQLSpec, a fixed, implementation-agnostic formalisation of SQL semantics; an isolated pipeline then checks code and proofs. On TPC-H and SEC-EDGAR, verified per-template code runs 22.0–61.3× faster than DuckDB and Umbra (geometric mean), and a verified general-purpose engine 1.27–3.4× faster on TPC-H. The pointed result: a testing-based LLM synthesis baseline returned wrong answers on 16 of 28 templates. Read it next to the firewall paper above. (Lao, Trummer) [paper] [unverified: template-specialised speedups are not comparable to a general engine's]
  • When is one query per template enough? Moving a learned cost model to new hardware — the same plans for 1,162 TPC-H/TPC-DS queries were timed on PostgreSQL in six environments (laptop vs server, all cores vs pinned to 1–2, small buffer pool). Most of the slowdown variance between machines lies between templates, so a single speed factor stops improving after a few queries. Separate serial and parallel lines plus a per-template offset, with one measured query per template, reach median Q-error 1.10 (TPC-H) and 1.19 (TPC-DS), close to retraining on the new machine; fine-tuning a DACE-style neural model gains at most 2%. On JOB nothing helps much (2.36 even after retraining). Tests were pre-registered, and two of five repeats at 10× scale missed. (Patel) [paper]
  • Fidelity synopses: choosing an ANN index configuration per query, before running it — the cardinality-synopsis idea applied to vector search. The embedding space is split into cells around landmarks, and each cell records how often each index configuration met a recall target on sample queries. At query time, one nearest-landmark lookup (21–32 µs batched) gives a calibrated estimate per configuration, and the optimizer picks the cheapest one that keeps the workload's miss rate within its requirement. On 5.8 M LAION items with four embedding models, cost falls to a median 0.72× of a static deployment in all 16 settings. (Ramanatha, Singh, Ramanath) [paper]
  • PQR-Search: per-query recall guarantees for ANN in dynamic vector databases — the measured problem first: indexes tuned to an average recall of 0.99 left 5–19% of in-distribution queries below it, and up to 99.6% of real out-of-distribution queries, with misses growing under updates — wrong rows for any filter, join or aggregate on top. The method guarantees Pr[recall(q) < τ] ≤ δ per query, using only a random rotation inside the index: 1-bit codes of rotated residuals against IVF centroids, pruned with exact error quantiles. The guarantee survives inserts and deletes, held in every audit on 20 datasets of up to 100 M vectors, and costs 2.5× HNSW's single-query latency. (Loh, Lee) [paper]
  • Eliminating servers in state machine replication — S²MR puts both the durable total order and the materialised state on disaggregated storage. Clients jointly maintain one copy of the state through the shared log, which becomes the only interface for SMR. The AirDB transactional KV store built on it is indifferent to server failures and badly behaved clients and starts 10–45× faster from cold than etcd over Raft. (Park, Hu, Yu, Balakrishnan, Park) [paper]
  • Quirinus: when deterministic concurrency control beats 2PL and OCC for geo-replication — an analytical model of 2PL, OCC and deterministic CC under geo-replication that identifies when ordering a batch before execution pays for its coordination. It then builds a DCC system with speculative execution, transaction reordering, CRDT integration and a fast-path commit: up to 6.2× Tiga's TPC-C throughput "even without these optimizations". (Mao, Zhang, Zhang, Jacobsen) [paper] [unverified: single configuration]
  • Recast: storage-resident ANN that handles deletes — raw vectors stay on disk and an IVF with a new quantisation (RecastQ) stays in memory.
