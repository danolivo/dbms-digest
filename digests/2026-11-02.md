# DBMS Weekly — 2026-11-02 (week of Nov 2–8)

_Days before 19 RC2, Andrew Dunstan reverted the "complete" immutability check for `to_json`/`to_jsonb` after it let `JSON_ARRAY()`/`JSON_OBJECT()` expression indexes go stale and return wrong rows; anything built on 19rc1 that depends on it must be redefined before dump/restore or pg_upgrade. Two of last issue's checkpoint races (ROLLBACK PREPARED, multixact creation) were fixed back to 14, and the 18.7/17.12/16.16/15.20/14.25 notes — "a good bit longer than average" — collect Memoize and Sort-node wrong results, a pg_trgm GiST corruption fix that needs a REINDEX, incremental backups restoring stale visibility-map bits, and a walsender lost wakeup that stalled synchronous commits for up to 10 s. The list's meta-story was AI-found bugs: one tester asked how to submit more than 1,000, Peter Geoghegan said he holds about 25 unreported ones and posted his own LLM-written rival to the nbtree prefix-compression patch. On the blogs, failover was the theme: Dimitri Fontaine killed primaries in a five-region pg_auto_failover + logical-replication system and counted every hole and duplicate, and Ubicloud and PlanetScale gave opposite answers to "how do you know the old primary is dead". Nikolay Samokhvalov put UUIDv4 keys at 0.62–0.69× an ordered key's insert rate once the index outgrows memory, Franck Pachot showed TOAST stops compressing mid-sized documents on 16/32 KB pages, AWS proposed upstream a constant-time binlog commit for huge MySQL transactions, Thomas Neumann took apart GenDB-V's 22–61× TPC-H claim, and PostHog explained why it is leaving DuckDB after five months._

## PostgreSQL

- **[UUIDv4 vs UUIDv7: what a random primary key costs in Postgres](https://postgres.ai/blog/20261105-uuidv4-vs-uuidv7)** — 18.6, 16 clients, one single-row INSERT per transaction, `synchronous_commit = on`, three tables differing only in the primary key (v4, v7, int8), hypotheses written down with falsifiers before the runs. Results: *(Nikolay Samokhvalov · postgres.ai)*
    - While the index fits in memory the key barely matters: UUIDv4 ran at 0.95–1.10 of v7, because the shared WAL flush sets the rate.
    - With a 1 GiB `shared_buffers` under a 3 GiB cgroup cap, v4 starts to fall at ~26 M rows, when its primary key outgrows shared_buffers. At 100 M rows it ran at **0.62–0.69 of an ordered key on the same server**, roughly one buffer read and one dirty-page eviction per insert, done by the backend itself.
    - v4 wrote **1.5–1.9× the WAL per row** at 90–100 M rows, because every checkpoint re-images each leaf it touched; its primary key was 33% larger than v7's.
    - v7 generated in the application with client clocks spread over ±60 s produced an index 69% full with 45% of leaves out of order, so generate it in the server.
    - `ORDER BY id DESC LIMIT 100` on a v4 table returns the largest random values, not the newest rows.
    - The predicted 0.5× was never reached. The post compares its results with Vondra's 2018 numbers (15–20% once past RAM, on SATA disks).
- **[Postgres logical replication beyond one writer](https://tapoueh.org/blog/2026/11/postgres-logical-replication-beyond-one-writer/)** — rebuilds what BDR did in 2014 from stock features: four regions plus a warehouse, each a pg_auto_failover group (monitor + three nodes), linked only by core logical replication. Row filters (15) and `origin = none` (16) prevent loops, failover slots with `synchronized_standby_slots` (17) keep slots across failover, and 18/19 count conflicts and sync sequences. A Docker lab is included and every number comes from three runs. *(Dimitri Fontaine · tapoueh.org)* `[by pg_auto_failover / pgcopydb author]`
    - A failover-slot consumer at ~25 rows/s: a planned failover lost and duplicated nothing (1.4–2.2 s); `kill -9` on the primary gave 2–4 duplicates and no holes (51–52 s); with `synchronized_standby_slots` emptied, 3–13 rows were missing and 69–92 rows had reached the consumer but not the new primary.
    - With 2,000 concurrent writes in each of four regions and two cascades, every node ended with exactly 8,000 rows.
    - DDL is the remaining gap. Pausing writers costs 0.9–1.5 s; pgcopydb captures DDL with an event trigger and `pg_logical_emit_message`. A fifth region joined a 600,000-row system with five statements.
    - Two writers updating the same 1,000 keys at 2,000 tps each are only counted as conflicts (18), not resolved.
- **[Fencing a Postgres primary that might still be alive](https://clickhouse.com/blog/fencing-a-postgres-primary-that-might-still-be-alive)** — promotion alone does not stop the old primary. A session can `SET synchronous_commit = local`, the other standby in an `ANY 1` quorum still acknowledges, and a COMMIT whose sync wait is cancelled is already in the local WAL. `pg_ctlcluster stop` is undone by auto-start on reboot, and a `pg_hba.conf` reload only affects new connections, so long-lived PgBouncer server connections survive it. The fences that work: *(Furkan Sahin · clickhouse.com / Ubicloud)* `[vendor blog — substantive]`
    - bare metal: `ip link set vetho<vm> down` on the host, which cuts clients, replication and WAL upload in one step
    - AWS: security groups are stateful and `stop-instances` is slow, so every server gets a second "user" NIC that is force-detached
    - GCP: a Dynamic NIC is deleted
    - All mechanisms run in parallel and the first success proceeds. If every one fails, the standby promotes anyway; this fail-open behaviour is deliberate and pinned by a test. Based on the author's PGConf.EU talk.
- **[Designing a reliable unplanned failover](https://planetscale.com/blog/designing-a-reliable-unplanned-failover)** — the sequel to last issue's planned switchover, and the opposite answer to the same question. Neki uses no lease; it asks the replicas. It fails over only when at least one reachable replica reports broken replication (`pg_stat_wal_receiver`) and none contradicts it, and it waits if it can reach neither the primary nor any replica. Short TCP keepalives, `tcp_user_timeout` and `wal_receiver_timeout` are tuned so that a crash, rejected connections, dropped packets and a frozen process all end the same way, as "replication broken". Under `ANY 1 (R1, R2, R3)` a primary nobody can ack cannot commit. Postgres has no `STOP REPLICA IO_THREAD`, so the replicas are kept from reconnecting to a returning primary by prefixing its host in `primary_conninfo` with `//`. *(Shlomi Noach · planetscale.com)* `[vendor blog — substantive]`
- **[PostgreSQL document compression: TOAST thresholds, storage policies, and page size](https://dev.to/franckpachot/postgresql-document-compression-toast-thresholds-storage-policies-and-page-size-oh4)** — TOAST tries to compress a value only once the whole tuple passes a hardcoded quarter-page gate (~2 KB at 8 KB pages). `toast_tuple_target` changes only the reduction target: lowering it cannot trigger compression, and raising it suppresses more. On source builds of 19rc1, a 3,868-byte JSONB document no longer compresses with 16 KB pages and a 7,708-byte one stops at 32 KB, because the gate scales with the block size. WiredTiger, by contrast, compresses whole leaf pages across documents. He links the 2019 `compress_tuple_target` thread (Deolasee, Dunstan, Paquier) and proposes an activation threshold separate from the inline target, or per-column eligibility. This matters to DocumentDB, which stores BSON through TOAST. All SQL and Dockerfiles are included. *(Franck Pachot · dev.to)*
- **[Patroni, Ubuntu 24.04, and two unplanned PostgreSQL failovers](https://dev.to/franckpachot/patroni-ubuntu-2404-and-two-unplanned-postgresql-failovers-52gl)** — an 8-hour load died with "SSL connection has been closed unexpectedly". The cause: unattended-upgrades upgraded `zlib1g` at 06:19:03, and needrestart ran `systemctl restart` on a list that included the custom Patroni unit. With the default `KillMode=control-group`, the stop signal reached Postgres too: smart shutdown, then fast, then failover. Hours later the new primary got its own unattended upgrade, giving a second failover. The post walks the evidence chain through the journal, the `apt-daily-upgrade` unit, `dpkg.log` and the unattended-upgrades dpkg log. *(Franck Pachot · dev.to)*

- **[systemd-sysusers and directory-managed Postgres accounts: avoiding startup failures](https://enterprisedb.com/blog/systemd-sysusers-and-directory-managed-postgres-accounts-avoiding-startup-failures)** — PGDG RPMs ship `/usr/lib/sysusers.d` definitions instead of `useradd` scriptlets: all packages from 18, and the Fedora packages from 14.19/15.14/16.10/17.6 (EPAS from 17.11/18.2). If the `postgres` account comes from AD/LDAP through SSSD, Winbind or Centrify, `systemd-sysusers` runs at early boot before the directory is reachable and creates a local account with a different UID. - **[A session-level advisory lock that quietly expires with `idle_in_transaction_session_timeout`](https://old.reddit.com/r/PostgreSQL/comments/1xq4pmx/our_postgres_lock_was_supposed_to_keep_two_jobs/)** — a Python driver opens a transaction on the first SELECT unless autocommit is on, so the connection holding the lock sits idle in transaction.
